# Decisions

Settled decisions and why, current state only. A changed decision is edited in place and its heading carries the date of the latest change; history is in git.

## Repository (2026-11-04)

- Default branch `master`. All repo text is English.
- Research and design drafts are never committed; only distilled, verified conclusions enter `docs/`.
- `AGENTS.md` is the single agent entry point; `CLAUDE.md` is a symlink to it.
- Standalone repository with nothing internal in it: it is meant to become public.

## Rails (2026-11-04)

The project runs on four rails, in order: lightness; a direct, obvious network architecture without invented or unneeded abstractions; minimal allocations; multithreading with no dependency on the Unity loop or main thread (IO, TLS and file writes on native threads, API callable from any thread, core assembly without `UnityEngine`). A change that trades one of them for convenience needs the owner.

## Stack (2026-11-05)

- Own shim in C11, not a fork of 4AVolcano/curl-unity: it exports the curl API, does not pin the NDK and carries an HTTP/3 stack; used only as a reference for curl flags.
- TLS: mbedTLS 4.1 LTS on every platform with a compiled-in Mozilla CA bundle (reasons in `docs/architecture.md` *TLS and trust*).
- Build: CMake + Ninja superbuild, sha256-pinned dependency tarballs in an immutable content-addressed cache; NDK r29, Xcode for Apple, `zig cc` for Linux and Windows (*Windows build*).
- Minimum OS: Android API 25, iOS 15.0, macOS 11.0, Windows 10, Linux glibc 2.17.
- Tests: own minimal C test harness + ctest JUnit; Python fault bench locked by `uv`; privileged network scenarios in a per-run Linux container; Wine in a container for Windows; Unity Test Framework in batchmode; arm64 emulator/simulator on the Mac.
- CI: local gate first, then CI running the same gate.
- Consoles and WebGL stay reachable through the shim's `platform/` layer and, later, a compile-time UnityWebRequest implementation of the same C# types. No backend interface now.

## Bootstrap and toolchain pins (2026-11-04)

- One idempotent `./scripts/bootstrap` sets up a machine or a fresh worktree with no manual steps: `brew bundle` from a checked-in `Brewfile`, the pinned NDK revision via `sdkmanager`, `uv sync` for the bench, the container images (test container by digest, Wine runners built from pinned bases), `dotnet restore`, then a version check against `scripts/versions.env` that fails loudly. Agents run it first; it is safe to rerun.
- Homebrew is not version-checked and Python only against a minimum (`PYTHON_MIN_VERSION`): neither reaches a shipped artifact, the bench's packages are locked in `uv.lock`, and both move under the repository with any `brew upgrade` (auto-update bumps Homebrew; a newer `python@3.x` pulled in as another formula's dependency takes over the unversioned `python3`). Tools that build artifacts stay pinned exactly.
- Xcode is checked, not installed; the pin is 27.2: ASan and TSan work with it on macOS 27 (clean programs exit 0, a heap overflow and a data race are reported). Bootstrap warns below 26.4, where they are broken on macOS 26.

## Native core: ids, events, shutdown (2026-11-04)

Shape per `docs/architecture.md` *Threading*: one owner thread per client, drain by poll or wait, no reverse P/Invoke.
- Ids are `(slot, generation)`; slots whose generation would wrap are retired. One `completed` per transfer; abort acts only on an unfinished transfer; results live until `ugo_release`.
- Memory bodies stay in one native buffer exposed as a span until release; no caller-supplied buffers.
- Events are stored in the transfer's slot plus a bounded queue of slot indices, not in a shared ring with reservations: no event capacity, `submit` fails only when no slot is free. One drainer at a time; headers of the final response travel in the `headers` event; progress only on change; intermediate progress updates are published at most once every 10 ms per transfer, and a count held by that limit is published before `completed`, regardless of the interval, so the last progress carries the final byte counts; phase metrics in `completed`.
- Shutdown wakes waiters first, frees nothing (destroy frees) and joins without a timeout.
- The ABI version is a field of the client config, not a separate `ugo_abi_version()`; struct layouts are checked in the gate, on the C# side by reflection.
- DNS TTL per client. No `max_host_connections`, no `FSYNC` flag.

## Clock, URL validation, stale client pointer (2026-11-04)

- `ugo_monotonic_us` and event times count system sleep on every platform (`CLOCK_BOOTTIME`, `mach_continuous_time`, `QueryInterruptTime`). Why: one meaning everywhere; a caller deadline that spans a device sleep fires on wake, when the connection is most likely dead. curl's own clock differs per platform and only drives curl's internal timeouts.
- `submit`/`ws_open` parse the URL with curl's URL API and pass the handle via `CURLOPT_CURLU`; a malformed URL or a wrong scheme for the call is `E_INVALID_ARG`. Why: a programmer error must not look like a network failure; one parse per request, no second parse in curl.
- Address reuse of a client pointer freed by `ugo_shutdown_all` is accepted, not guarded by tombstones: in Unity the old domain's code has stopped before the new domain's first `create`, and IL2CPP players have no domain reload.

## Abort (2026-11-05)

- Stopping an operation is "abort" on every surface: `ugo_abort`, `UgoClient.Abort(UgoId)`, `UgoWebSocket.Abort()`. Why: it is the Unity/.NET norm (`UnityWebRequest.Abort`, `ClientWebSocket.Abort`, `HttpWebRequest.Abort`), and one surface should not have two verbs for one action.
- The class is `ABORTED`; its detail names the cause: `CALLER` (`UgoErrorReason.Caller`), `SHUTDOWN`, `BACKGROUND_EXPIRED`.
- `CancellationToken` parameters stay: it is the BCL type callers already hold. A triggered token aborts the operation, as `Abort` does.

## Methods, request bodies, implicit headers (2026-11-04)

- Any RFC 9110 method token, standard or custom; the public type is `System.Net.Http.HttpMethod`. The ABI carries the method as a validated token (≤ 32 `tchar`s, case-sensitive, no normalisation, unlike HttpClient). The curl mode follows the body, not the method; `CUSTOMREQUEST` names the method. The body is independent of the method.
- HEAD sends and reads no body; HEAD with a body is `E_INVALID_ARG`. CONNECT is rejected as invalid input: no tunnel lifecycle.
- `UGO_BODY_NONE` means no body at all; the managed layer turns an unset body into an empty one for every method except GET, HEAD, DELETE and OPTIONS, so POST, PUT, PATCH, TRACE and custom methods send `Content-Length: 0` as HttpClient does.
- Implicit-header suppression appends curl's `Name:` removal lines only for names the caller did not send, and never `Content-Type:` for multipart (curl derives the boundary header from it).
- Request bodies are sent exactly as given and never compressed (contract *Request body*): a caller may sign the wire bytes.

## Response bodies, caps, timeouts (2026-11-04)

- Non-2xx bodies are delivered for memory responses. A non-2xx response to a file download writes no file; its body is kept in memory up to `UGO_ERROR_BODY_MAX` (64 KiB: enough for JSON or HTML error pages, small against the default 16 MiB memory cap). An empty 2xx file response creates or truncates the file in `finish`.
- A body over its memory cap aborts the transfer instead of draining and dropping the rest: a misbehaving server cannot make the client read an unbounded error page. The result keeps exactly the cap bytes. A non-2xx response stays `HTTP_STATUS` (detail `MEMORY_LIMIT`), for memory sinks too, so status-based retry policy sees the status; a 2xx is `TRANSFER`.
- The file sink deletes its partial file on abort or failure before `completed`, unless the request asks to keep it or to resume: the same behaviour as UnityWebRequest's `removeFileOnAbort`, and callers never race the native writer.
- Low-speed abort is per request, both values or neither, seconds in the ABI (curl's granularity). The managed API names it by its main use: `StallTimeout` is how long the speed may stay below the threshold, rounded up to whole seconds like the other durations, and alone means 1 byte per second, the lowest threshold curl takes. The speed is curl's average over its last 5 seconds (`CURL_SPEED_RECORDS`, `lib/progress.c` at `curl-8_23_0`), so silence after an active transfer is noticed about 5 s later than the timeout; `MinimumSpeedBytesPerSecond` is an optional higher threshold and is rejected without it. Why: a threshold and a window that must be set together hid the one knob that ends a request the server never answers. It stays off by default: any value breaks long polling.

## Resume of an interrupted download (2026-11-05)

Mechanics in `docs/abi.md` *Transfer lifecycle* and `docs/architecture.md` *Bodies*.
- **Off by default, opt-in per request** (`UGO_REQ_RESUME`, `UgoRequest.Resume`). A request without the flag is a plain download (truncating sink, no `Range`/`If-Range`/`Accept-Encoding: identity` added, no extra file IO).
- **The file is the only state.** If `sink_path` holds bytes, continue from its length; keep it on failure. No sidecar, no stored validator, no explicit offset in the ABI. Why: the contract leaves naming, commit and validation to the caller, and hidden library state next to the `.part` would have to be named, cleaned up and kept consistent with the caller's own. Control stays with the caller without new knobs: an `If-Range` header with the first response's strong `ETag`, or its `Last-Modified` only when there was no `ETag` and the date is strong (RFC 9110 §13.1.5; a weak `ETag` is forbidden there), so the server turns a mismatch into a `200`, which restarts the file; and shortening the file to resume from an earlier verified point.
- **Outcomes:** a `206` that starts at the file length appends, held to exactly its `Content-Range` whatever the framing; any other `2xx` (server ignored `Range`, or `If-Range` failed) rewrites from zero; `416` with `Content-Range: bytes */<file length>` is success with status 416 and nothing written (the curl CLI's `-C -` treats a complete file the same way); everything else fails `TRANSFER` / `RESUME_MISMATCH` (one detail, no new class: the host is not to blame, a retry is cheap). A **short `206`** (complete range, ends before the stated total, as chunking CDNs do) is `TRANSFER` with detail `NONE` and the file kept: the caller's policy for it is the one for a cut connection, resume again, and each attempt makes progress. **Delete only on contradiction:** the file is deleted only when the server contradicts it (a `206` starting elsewhere, a `416` reporting a shorter resource), since the caller's ordinary retry then starts from zero instead of failing the same way; a response that is merely inconsistent in itself (no or repeated `Content-Range`, multipart, a length that disagrees with the range, a `416` reporting a longer resource) says nothing against the bytes on disk, so they are kept. An explicit `UGO_REQ_KEEP_PARTIAL` always wins: the caller may continue the file from another origin. A matching `416` stays under the 64 KiB error-body cap like every non-2xx body: `HTTP_STATUS` / `MEMORY_LIMIT` if its body overflows, file untouched.
- **Identity encoding.** A resuming request sends `Accept-Encoding: identity` unless the caller sets the header, and is never decoded. Why: ranges count bytes of the encoded representation; a file of decoded bytes has no offsets a server can continue. OkHttp makes the same call (no transparent gzip when the request has `Range`).
- **Counts:** progress of an appending `206` is whole-file (offset added to received; total taken from the checked `Content-Range`, never offset + `Content-Length`, which could overflow), so a progress bar needs no caller arithmetic (UnityWebRequest makes callers add it themselves); `completed.bytes_received` stays this transfer's wire bytes; `headers.resume_offset` says where the body continues.
- **Rejected:** `CURLOPT_RESUME_FROM_LARGE` (fails a `200` with `CURLE_RANGE_ERROR`, trusts a `200` whose length equals the offset, accepts any `416`, checks only the range start; see architecture.md *Verified upstream facts*); a library-kept validator sidecar (aria2's `.aria2`, iOS `resumeData`), which is hidden state outside the caller's naming; an explicit offset field, which a caller gets by shortening the file; refusing to resume without a validator (iOS requires `ETag`/`Last-Modified`), which breaks the common case of content-addressed asset URLs and is the caller's call through `If-Range`.

## Response compression (2026-11-05)

Responses are decoded; request bodies are never compressed (*Methods, request bodies, implicit headers*). Compared against OkHttp, `HttpClient`'s `AutomaticDecompression` and curl's own `--compressed`.
- **zlib 1.4**, pinned by version and sha256 like the other dependencies, built from source (`ZLIB_BUILD_SHARED=OFF`) for every target and linked statically into `libugo`; curl is built with `CURL_ZLIB=ON` pointing at that `libz.a`, never at an OS copy (Android's NDK and iOS ship a system zlib of their own version). No brotli or zstd: gzip is what every CDN and API server can serve, and each extra codec costs size on every platform. The tarball comes from the GitHub release: zlib.net keeps only the current version, so its URL would break at the next release. zlib costs 16–33 KB per target, within `LIBUGO_MAX_BYTES`.
- **Transparent, OkHttp-style.** Without a caller `Accept-Encoding` the library sends `Accept-Encoding: gzip` (`CURLOPT_ACCEPT_ENCODING`) and delivers the decoded body; a caller `Accept-Encoding` header, a removal line included, turns decoding off and the body arrives as received. Why: a caller header of that name wins like every implicit header, and a caller asking for an encoding itself wants the encoded bytes (a pass-through cache, a signed body). No per-request knob in the C# API: the header is the opt-out. A resumed download is never decoded (*Resume of an interrupted download*).
- **Only `gzip` is advertised, `deflate` is still decoded.** Why: `deflate` gives no size advantage over gzip (the same DEFLATE stream), and servers have disagreed on whether it means zlib-wrapped or raw data; curl decodes both, so a server that sends it unasked still works.
- **Caps count decoded bytes.** `memory_limit`, the 64 KiB error-body cap and the file see what curl's decoder writes, so a small compressed body cannot expand past a cap (a gzip bomb stops at the cap, with `MEMORY_LIMIT`). The file sink has no decoded-size bound: hosts are trusted (owner's call). Headers, `Content-Length`, progress and `bytes_received` stay on the wire's encoded bytes: they are curl's counters, and progress against `Content-Length` stays consistent.
- **A body that fails decoding is `TRANSFER`, detail `NONE`.** The raw code tells corrupt data and unknown codings (`CURLE_BAD_CONTENT_ENCODING`, 61) from bytes after the end of the stream (`CURLE_WRITE_ERROR`, 23); no new detail: retry policy is that of a cut connection, a bad response from that host. A bare `CURLE_WRITE_ERROR` maps to `TRANSFER`, not `LOCAL_IO`: every write failure of the shim's own callbacks already carries its class, so a bare 23 is the decoder's, and the contract forbids blaming the disk for the server. A stream that ends early inside complete framing is caught by a curl patch (*curl patch: unfinished content coding*).

## curl patch: unfinished content coding (2026-11-05)

- curl 8.23.0 reports success with the decoded prefix when a gzip or deflate stream ends before its end marker while the HTTP framing is complete (`Content-Length` reached, last chunk, HTTP/2 `END_STREAM`): nothing checks that inflate reached the end. That is a made-up success for a truncated config or bundle, and the shim cannot see it (zlib state and wire bytes stay inside curl). The fix is a narrow patch to the pinned curl through the emergency patch path the contract promises (*Updates*): waiting for upstream leaves a truncated body reported as success. What the patch does, its upstream status and drop condition: patches.md *curl-8.23.0-unfinished-content-encoding.patch*.

## Redirects (2026-11-06)

- **HTTP:** curl follows redirects itself up to the request's limit (0 delivers the 3xx). `CURL_REDIR_POST_ALL` keeps POST a POST on 301 and 302; the body is replayed on every followed hop (`SEEKFUNCTION`). `Authorization` and `Cookie` go only to the original origin.
- **303** (RFC 9110 §15.4.4: replaying a non-idempotent request can repeat its side effect) becomes GET (HEAD stays HEAD) with no body and without the caller's `Content-Type`, `Content-Length`, `Content-Encoding` and `Transfer-Encoding`; other headers follow the usual redirect rules. On a 303 the header callback marks the hop, `CURLOPT_PREREQFUNCTION` aborts curl's next request before a byte of it is sent, and the owner re-adds the same handle with curl's resolved target (`CURLINFO_EFFECTIVE_URL`), `CURLOPT_HTTPGET` (HEAD keeps `NOBODY`), the filtered header list, `MAXREDIRS` minus the hops already followed and the rest of `total_timeout_ms`. Why this hook: it is the only one between curl following a 303 and sending its request; by then curl has read the 303 to its end, resolved `Location`, applied its redirect-protocol rule and counted the hop, so the limit, `TOO_MANY_REDIRECTS` and scheme failures stay curl's. Failing the 303 in the header callback would also work but abandons its body mid-read.
- **303 credentials:** the re-issue is a new transfer to curl, whose own `Authorization` rule then compares against the 303 target; the shim therefore drops `Authorization` and `Cookie` itself when the target is not the original origin. A caller `Host` is dropped there too: the re-issue makes the 303 target curl's initial origin, where curl sends a custom `Host` (`lib/http.c`, `lib/transfer.c` at `curl-8_23_0`).
- **303 cost:** on HTTP/1.1 the connection curl selected for the next hop is closed, because the pre-request callback runs once that connection is chosen (`multistate_do`, `lib/multi.c` at `curl-8_23_0`) and curl treats any callback abort as premature and closes a non-multiplexed connection after one (`multi_done`); that is the connection the 303 came on only when curl picked it again for the next hop. The GET then takes another connection, new or pooled. HTTP/2 keeps its connection.
- **Rejected for 303:** curl's `CURLFOLLOW_OBEYCODE`, which switches the method but keeps caller-set headers (`lib/http.c` at `curl-8_23_0`): the managed layer always sets `Content-Type`, so a GET would carry it, and a caller-set `Content-Length` would make the server wait for a body that never comes. Following every redirect in the shim, which would move body replay, rewinds and the rules of 301/302/307/308 out of curl.
- **WebSocket handshakes** follow a 3xx with `Location` with the HTTP semantics: up to 10 hops (the managed HTTP default; no ABI field), `wss` → `ws` allowed as `https` → `http` is, `Authorization`, `Cookie` and a caller `Host` only to the original origin (the same filter as the 303 re-issue), too many redirects `TRANSFER` / `CURLE_TOO_MANY_REDIRECTS`. Why: a WebSocket URL behind a redirect works as an HTTP one does, with no redirect loop in every caller. The shim, not curl, re-issues the handshake: curl 8.23.0 fails any final response to an upgrade as `CURLE_HTTP_RETURNED_ERROR` in `http_on_response` (`lib/http.c` "Refused WebSocket upgrade") before `multistate_performing` (`lib/multi.c`) reaches its follow branch, so `CURLOPT_FOLLOWLOCATION` never acts on a `ws`/`wss` transfer. The shim removes the handle, sets the resolved URL and headers and re-adds it; curl then starts a new transfer whose origin is the new URL, which is why the shim drops the credentials (`Curl_auth_allowed_to_host`, `lib/vauth/vauth.c`, compares against the transfer's first origin).

## Contract scope for a public library (2026-11-06)

- **Decision:** the contract describes a public library. What the base specifications require of a client (RFC 9110/9112/9113, RFC 6455) is in, implemented or listed in debt.md; optional features and extensions are in only where the contract names them. Under it: WebSocket binary messages (an RFC 6455 data frame type, expected of any client) and GET after 303 (*Redirects*).
- **Kept out:** permessage-deflate (RFC 7692 extension). curl 8.23 has no support and rejects RSV1 frames, so it needs a curl patch or our own framing in `CURLWS_RAW_MODE`, plus a zlib inflate and deflate context per socket (hundreds of KB each with the default window), against rail 1; many servers leave it off for that memory, and applications can compress payloads in binary messages. Proxies stay out (`PROXY` in the disabled-feature list, `native/deps/CMakeLists.txt`), the OS trust store too (architecture.md *TLS and trust*).
- **Stated:** the connection bound counts TCP connections, not HTTP/2 streams, and a transfer queued natively for a free connection spends its connect and total timeouts while waiting (`lib/url.c`, `lib/multi.c` at `curl-8_23_0`).

## Fire-and-forget and iOS finish in background (2026-11-05)

- Two per-request flags cover posts whose caller keeps its own durable copy (telemetry, logs): `detached` (no events, self-freeing; `EnqueueDetached` reports acceptance only) and iOS `finish_in_background` (background task from submit to finish). Mechanism in `docs/architecture.md` *Finish in background (iOS)*.
- The background task is begun before the client lock is taken: UIKit runs the expiration handler on the main thread, which takes that lock. It is ended exactly once, by `finish` or by the handler; expiry finishes the transfer as `ABORTED` / `BACKGROUND_EXPIRED`, like an abort. The handler reaches the client through the process-wide live list, so a client destroyed meanwhile is never touched.
- Objective-C with ARC (`platform/ios.m`): the block and the slot share the task object without manual lifetime code.
- Tested in the iOS simulator player (`ios-player`, `docs/testing.md`). The test player disables Unity audio: its audio session holds media assertions that keep the app running in the background, which hides both suspension and expiry.

## WebSocket protocol handling (2026-11-06)

- Own control-frame handling and handshake check on top of `curl_ws`: curl 8.23 auto-PONG is broken and `Sec-WebSocket-Accept` is not verified. `headers(101)` is emitted after the Accept check and means open; the socket's end is its one `completed`.
- A slow consumer pauses receiving rather than dropping or closing.
- `ugo_ws_send` copies into a per-socket send buffer allocated at `ws_open`; no borrow, no send-completion event.
- **A protocol error ends the socket once our CLOSE is out.** After the first protocol error the shim finds (invalid UTF-8, a bad CLOSE, a message over `max_message_bytes`), it neither reads nor parses another frame: the socket leaves the poll set for reading, the CLOSE with the matching code goes out under `close_timeout_ms`, and the socket ends `TRANSFER` as soon as that CLOSE is written, without waiting for the server's. Why: RFC 6455 §7.1.7 fails the connection at once; a server that keeps sending after its own error would otherwise keep the socket alive until the close timeout, and every further frame would be parsed for nothing. Framing errors curl's decoder finds still end without CLOSE: debt.md *Framing errors close without CLOSE* says why.

## WebSocket API (2026-11-06)

Judged against `System.Net.WebSockets.ClientWebSocket`, OkHttp's `WebSocketListener`, Best HTTP and NativeWebSocket.
- **ABI v2:** `ugo_ws_send` takes a `type` (`UGO_WS_TEXT` = 1, `UGO_WS_BINARY` = 2, the RFC 6455 opcodes) rather than a sibling `ugo_ws_send_binary`; `ugo_ev_ws_message` carries `type`. Why: one export, one P/Invoke and one argument check; the type rides in the upper half of the 8-byte header each queued message already carries, so a binary message costs no extra send-buffer room.
- `UgoClient.OpenWebSocket(in UgoWebSocketRequest, UgoWebSocketListener listener = null)` returns a `UgoWebSocket`; a refusal throws `UgoSubmitException` as `SendAsync` does. The handler is fixed at open, so no event can arrive before the caller subscribes (the race of Best HTTP's subscribe-then-`Open` is gone).
- Dual form over one core, as for HTTP. Callback: an abstract `UgoWebSocketListener` with `OnOpen`/`OnMessage`/`OnClosed` (OkHttp's shape; one class instead of three delegates and their closures, one instance may serve many sockets; failure folds into `OnClosed` because every socket ends with one `completed`). Awaitable, when no listener is given: `WaitOpenAsync()` and `ReceiveAsync()` (one at a time, as `ClientWebSocket.ReceiveAsync`), the end marked by `UgoWebSocketMessage.IsEnd`; both are `ValueTask`s over one internal source object per socket, allocated at open, so `IValueTaskSource` stays off the public type.
- Names follow `System.Net.WebSockets`: `UgoWebSocketMessageType { Text, Binary }`, `UgoWebSocketMessage.MessageType`, the payload span `Data`.
- `UgoWebSocketMessage` is a struct over the native backlog; `GetText()` allocates only when called and throws `InvalidOperationException` on a binary message. In a listener a message is valid during the call and the library releases it on return; in the awaitable form `Dispose()` releases it and every earlier one (the ABI's `through_seq`). `Data` of a released message throws `ObjectDisposedException` (one volatile read of the socket's highest released sequence) instead of reading recycled backlog memory. Unreleased messages are the back-pressure, so nothing is copied to managed memory.
- `Send(ReadOnlySpan<byte>, UgoWebSocketMessageType)` and `Send(string)` (text) return `UgoWebSocketSendStatus` (`Accepted`, `BufferFull`, `NotOpen`): a full buffer is normal flow for a game loop, not an exception. No single-argument span overload, so a span never silently means text. A span, not `ReadOnlyMemory`, unlike the borrowed HTTP inputs: the bytes are copied before return, and a span also takes `stackalloc` and pooled memory. `Send(string)` encodes into stack or pooled memory. Outgoing text is validated natively (`utf8_valid`, in place, before the lock); the managed layer maps `E_INVALID_ARG` to `ArgumentException`, telling invalid UTF-8 from an oversized message by the send-buffer size it keeps.
- `Close(code = 1000, reason)` returns false when the socket is not open and throws for a code an endpoint may not send or a reason over 123 UTF-8 bytes; `Abort()` drops the socket without a CLOSE frame. No `CancellationToken`: `Abort` and `Dispose` cover it without a registration per socket.
- `UgoWebSocketResult` carries the error class and reason (who sent the first CLOSE), the close code, the handshake as `Handshake` (a refused handshake or the 3xx past the redirect limit) and the CLOSE reason or error text; its spans live until the socket is disposed. Handshake headers have one shape, `UgoHeadersEvent`: `OnOpen` gets it, `UgoWebSocket.TryGetHandshake` returns the stored 101 to both forms while the socket runs (the awaitable form needs the negotiated subprotocol or a session header at open), `UgoWebSocketResult.Handshake` builds it from the result. `UgoWebSocket.Dispose()` aborts a running socket and frees its slot once closed.
- `UgoWebSocketState` is `Connecting`, `Open`, `Closed`, all set by the draining thread. No `Closing`: only a local `Close` could set it, a server or protocol close cannot be seen before `completed`, so it would lie half the time; `Send`'s status is the authoritative answer to "can I send".
- Client shutdown and disposal close every socket with `Shutdown`; WebSocket events never surface in `TryWaitEvents`, in manual mode they are dispatched inside it like `Send` callbacks.

## Public C# API shape (2026-11-05)

- Code name `UgoHttp` (namespace, assemblies, types) per .NET naming guidelines; the repo, brand and package display name stay `UgoHTTP`. Public types keep the `Ugo` prefix: no clash with `System.Net.Http` or callers' own `HttpRequest`.
- Dual, as in .NET: every operation has an awaitable form and a callback form over the same core.
- Drain: chosen per client at creation. Default background mode: one library-owned drain thread per client (started lazily, stopped by shutdown) completes awaitables and runs callbacks; the caller moves to its own thread if it needs one. Manual mode: the caller drains on a thread it picks, as rail 4 states; awaitables and callbacks complete inside that drain call. Raw draining is unavailable in background mode. Why: an awaitable must complete in the Editor and plain .NET with nothing pumping.
- An aborted request completes like any other in both forms: a response with an `Aborted` error, or the real result when the abort came too late. No `OperationCanceledException`.
- Request headers: an ordered name/value list, duplicates allowed, CR, LF and NUL rejected; no curl header syntax in the public API.
- The ABI mirror types (`ugo_*` structs, constants) are internal; the public surface is typed managed views.
- Public input buffers are `ReadOnlyMemory<T>` (bytes, form parts, header lists, CA bundle): the netstandard2.1 idiom, and pooled or native-backed memory works without a copy. WebSocket send takes a span (*WebSocket API*).
- An exception escaping a user callback or event handler is rethrown on the thread pool (async-void semantics) in both drain modes; draining continues. Plain .NET treats it as unhandled.
- `EnqueueDetached` has only the synchronous form: its result is acceptance, known on return.
- The operation bound is named `OperationSlots`, not `MaxOperations`: it is the size of the preallocated slot table, counts finished operations not yet disposed, and a caller reading it as a concurrency limit sets it too low. 0 means `DefaultOperationSlots` (64), so `new UgoClient()` works: about 1 KiB of native memory per slot, and 64 is the size the per-client memory figures were measured at (debt.md). A submit past it still fails with `NoCapacity`; no queue (contract.md *Concurrency*).

## Completion sources under Unity's corlib (2026-11-05)

- Every reused `ManualResetValueTaskSourceCore` in the package (`UgoOperation` per HTTP slot, the socket's open and receive sources) reports `Pending` from `GetStatus` while the draining thread's `SetResult` still touches the core: until it returns, or until it hands over to the registered continuation. Continuations are registered on the core as a fixed callback cached per source; it drops the flag under the same lock, then calls the caller's continuation outside the lock, so a continuation run inline by `SetResult` sees its operation complete. Execution and synchronization context handling stays the core's: the fixed callback is registered with the caller's flags. Why: Unity's corlib (Mono and IL2CPP, 6000.0 and 6000.3) marks the core complete before `SetResult` publishes its continuation slot, and its `GetStatus` checks only the mark; .NET's also requires the slot published, which closes the polling window without waiting for `SetResult` to return. A caller that polls `IsCompleted` or calls `AsTask()` in that window takes the result, the source resets, the caller starts the next wait, and the unfinished `SetResult` then invokes or poisons that wait's continuation: `InvalidOperationException` from `GetResult`, a stale result, or a continuation run twice.
- Not reproducible on .NET (`tests/dotnet`): its corlib already has the check. The regression test is `StressTests.PolledResultFollowedAtOnceByTheNextWait` in Unity EditMode (2 s after every worker is connected, at least 200 pairs per worker); without the flag a console run of the same loop on Unity's Mono fails within 2 s every time. `ContinuationSeesItsOperationCompleted` (dotnet and EditMode) and `ReceiveContinuationSeesItsMessage` check that a continuation sees its operation complete.

## CA bundle parsed once per client (2026-11-05)

Mechanics and curl facts in `docs/architecture.md` *TLS and trust* and *Verified upstream facts*.
- **Decision:** the shim parses the client's bundle (built-in or the caller's) into one `mbedtls_x509_crt` and gives it to every connection from `CURLOPT_SSL_CTX_FUNCTION` with `mbedtls_ssl_conf_ca_chain`; curl gets no `CURLOPT_CAINFO_BLOB`. Same path on every platform; mbedTLS types stay in `ugo.c`, out of the C ABI and C# API.
- **Why:** curl clones, SHA-256-hashes and reparses a blob on each new connection. Measured on loopback against the bench (macOS arm64, HTTP/1.1 with `Connection: close`, median of 300 handshakes, `appconnect_us - connect_us`): 2.7–3.0 ms with the 200 KB bundle as a blob against 0.75–0.85 ms with only the bench CA; with one parse per client both are 0.73–0.82 ms.
- **When:** lazily, at the client's first TLS connection, on the owner thread. Not in `ugo_client_create`: that call may come from the Unity main thread (Rails: TLS work stays off it), and a client that never opens TLS pays nothing. The callback runs only on the owner thread, so the chain needs no lock.
- **Parse failures:** cache only a successful parse. Every failure frees the partial chain and keeps the PEM for another attempt at the next connection; an explicit X509 or PEM allocation error returns curl 27, other failures curl 58. A positive skipped-certificate count can hide a transient allocation failure, so it cannot establish that the bundle is permanently invalid. Caching a rejection would make one transient OOM break every future TLS connection of that client.
- **Invalid bundle:** fails at each TLS connection with class `TLS` and curl 58, `create` still `OK`; the message names the bundle. A bundle in which some certificates parse and others do not is refused whole: a caller who ships a bundle expects every root in it to be trusted, and a silently shorter trust list only shows up as a verification failure on some host later. The built-in bundle parses fully (the native test sees curl 60 against the bench, not 58).
- **`UGO_CLIENT_TLS_INSECURE_DEV`:** no callback, so no chain is loaded with verification off.

## mbedTLS configuration (2026-11-06)

In `native/deps/client_config.h`:
- `MBEDTLS_DEBUG_C` is undefined. Why: curl calls into it only when built with `MBEDTLS_DEBUG`, yet the record path still paid for it (1.2% of owner-thread CPU on a 5×20 MiB HTTPS download, Pixel 7a), and `libugo.so` shrinks by 60 KB on android-arm64.
- `MBEDTLS_PSA_ASSUME_EXCLUSIVE_BUFFERS` is defined: otherwise PSA allocates and copies buffers per TLS record and per WebSocket mask, contradicting architecture.md *Allocations*. All buffers passed to PSA are private to the process; no untrusted process can modify them during a crypto operation. The built-in GCM and ChaCha20 drivers allow exact in-place input/output (`input == output`), and mbedTLS CI exercises this configuration.
- `MBEDTLS_CIPHER_C` is disabled by removing PSA unauthenticated cipher modes, CMAC, its PBKDF2 variant and NIST key wrapping; AES-GCM uses the one-block cipher layer (`MBEDTLS_BLOCK_CIPHER_C`), which calls AES directly; the four-block GCM patch below is compiled only with this layer. Why: 17–38 KB less per library (android-arm64 1,208,248 → 1,169,824 B without the patch) and about 7–13% faster on 1 KiB records on a Xiaomi 24129PN74G and a Pixel 7a; on 16 KiB records the layer alone changed nothing on the Xiaomi and 3–5% on the Pixel. Cost: TLS 1.2 CBC suites and the removed PSA algorithms are unavailable; TLS 1.2 AEAD suites and TLS 1.3 remain.
- `MBEDTLS_AESCE_C` is off for Windows ARM64 (*Windows build*).
- AArch64 AES-GCM runs four blocks at a time, through a patch to the pinned mbedTLS (patches.md *mbedtls-4.1.1-aesce-gcm-4block.patch*). Why a patch rather than waiting: the stock loop waits on one AESE chain per block, so a phone core stays near 1 GiB/s whatever layer dispatches AES; one-shot 16 KiB record decryption went 1041 → 4864 MiB/s (AES-128) and 1041 → 4045 MiB/s (AES-256) on a Xiaomi 24129PN74G, 894 → 3451 and 690 → 2909 on a Pixel 7a, 1 KiB records 2.2–2.7×. Upstream's multi-block path (TF-PSA-Crypto PR #702) is unmerged.

## Editor and Play Mode lifetime (2026-11-05)

- The API works in the Editor outside Play Mode without any pumping, so editor tools need no workarounds (unlike Best.HTTP, whose scheduler must be driven from outside). Domain reload aborts in-flight transfers; clients orphaned by a previous domain are shut down on the next init.
- Clients created while entering or running Play Mode are disposed on `EnteredEditMode`, after game shutdown callbacks. Why: stalled transfers and open WebSockets of Play Mode code must stop when Play Mode ends, while requests from `OnDestroy` must still be accepted before the cleanup. Best HTTP 3 is prior art: `HTTPUpdateDelegator.OnApplicationQuit` calls `HTTPManager.OnQuit` to abort globally, then `EnteredEditMode` resets setup; UgoHTTP preserves edit-time clients instead of aborting globally.
- The glue snapshots live clients on `ExitingEditMode` and disposes live clients absent from that snapshot on `EnteredEditMode`. Why: the existing weak registry and its constructor lock already define registration on any thread; one strong set in the glue needs no flag, constructor tagging, second registry or setting. Domain reload disposes the old domain's clients, so a null snapshot in the new domain correctly means empty. Disposal runs outside the registry lock and never calls `ShutdownForDomainUnload`, leaving new clients possible in Edit Mode.

## Glue assembly survives stripping (2026-11-04)

- `UgoHttp.Unity` is marked `[assembly: UnityEngine.Scripting.AlwaysLinkAssembly]`. Why: no game code references the glue, so UnityLinker never processes it and removes the whole assembly, `[RuntimeInitializeOnLoadMethod]` included. With the attribute, UnityLinker (High) keeps `Lifetime.Install` and `UgoClient.ShutdownForDomainUnload`. `[Preserve]` inside the glue would not help: the linker never opens an unreferenced assembly; the attribute is the documented switch for exactly that and needs no extra asset, unlike `link.xml`.
- The ABI mirror types need no rooting. UnityLinker (High) run on a root that uses `UgoClient` and never calls `UgoAbi.Dump()` keeps every field of every mirror struct it keeps, unused `reserved` fields included (sequential layout), and drops only whole unused structs. A struct the code passes or reads is therefore never shortened.

## Editor tracker (2026-11-05)

- **Decision:** an Editor window lists live clients and the slots they hold, from the existing weak client list and slot tables, plus a static ring of 512 released rows. The editor assembly turns tracking on at load, so each client and slot gets method, URL and start time; the only toggle is **Capture Stacks**. The window lives in an editor-only assembly that sees the core's internals; the core keeps no reference to `UnityEngine`.
- **Why a tracker:** a response, socket or message the caller forgets to dispose pins a slot until the client refuses new work (`NoCapacity`), and responses are structs without finalizers, so nothing else reports it. UniTask's `TaskTracker` and R3's `ObservableTracker` are the prior art. Reusing the slot table keeps one source of truth and costs one reference per slot; a separate registry would duplicate the lifecycle.
- **Why always on:** turning tracking on later cannot enrich objects created before, so a window opened to find a leak would show rows without URLs. The per-operation metadata is cheap next to an HTTP transfer; the stack walk is not, so it stays opt-in. The held-message counter is a plain store on every delivered message, independent of the switch.
- **Why a ring and a timer:** a short request can start and be released between two refreshes, so history has to be recorded at release, not diffed from snapshots. The count bound keeps memory bounded; ordinary released rows expire 10 s after release so finished work does not bury live rows. Slots archived by client disposal are `Closed with client`, neutral, and expire the same way: disposal can deliver a pending response before its await continuation runs, and disposal from a callback is supported, so a slot still held then does not prove the caller forgot it. Only `Reclaimed at Play Mode exit` is leak evidence and stays until ring eviction, since the exit sweep would otherwise erase the evidence the window exists for. Detached requests are not listed: they hold no managed slot and cannot be leaked by the caller.
- **Players: a switch only the Editor sets, not compile-out.** The core is one assembly built once per platform; a define limited to the Editor and tests would make the shipped core differ from the one the .NET tests check, including their allocation tests. In a player the cost is one volatile read per client creation, submit, WebSocket open and client disposal, one null check per release and one plain sequence store per delivered WebSocket message; no per-operation metadata or history is allocated, and the tracker type has one static lock object.

## Apple artifacts (2026-11-05)

Build mechanics are in `docs/architecture.md` *Build*.
- **macOS:** one universal `Plugins/macOS/ugo.bundle`, Editor + standalone, as the contract states. Why a bundle and not a universal dylib: it is the loadable-plugin form Unity documents for macOS, carries an `Info.plist` that signing and notarization of a standalone build expect, and is what established native Unity plugins ship. Ad-hoc signature because arm64 macOS refuses unsigned code; a game re-signs it with its identity. The per-arch `libugo.dylib` is never staged: two plugins named `ugo` in one Editor collide.
- **iOS:** `Plugins/iOS/libugo.xcframework`, static, `__Internal`, each archive one prelinked relocatable object with only `ugo_*` global. Why: an app that also links another SDK's curl, mbedTLS or nghttp2 must not clash (`verify` links such an app). `-fno-common` because two tentative definitions survived the prelink as private-extern commons under linker-generated names (`l3695`) that a second prelinked SDK could share and silently merge.
- **Size budget on iOS** is the growth of a dead-stripped app that references every export, not the archive: the archive carries relocations and code the app link drops.
- **`CMAKE_OSX_*` as cache entries:** without them the x86_64 slices silently built for the host architecture (dependencies set CMP0126 OLD).
- **Older consumer Xcode:** Apple static libraries must link with a consumer Xcode older than the build Xcode. A weak import of an availability-gated API still requires that symbol in the consumer's linking SDK: curl's iOS 27 `pipe2` path breaks an archive link with Xcode 26.2 even though the deployment target is older. curl is built with `HAVE_BUILTIN_AVAILABLE=OFF` on every Apple target, so its wakeup pipe uses `pipe` and `fcntl(FD_CLOEXEC)` instead of `pipe2`; the cost is two extra `fcntl` calls per client wakeup pipe, not per request or wakeup. `verify` rejects any weak undefined symbol in each iOS static slice and each macOS dylib and bundle slice, naming the symbols.

## Windows build (2026-11-05)

Mechanics in `docs/architecture.md` *Build*.
- `ugo.dll` for x64 and ARM64 is built on the Mac with `zig cc -target x86_64-windows-gnu` / `aarch64-windows-gnu` (pinned `ZIG_VERSION`, the Linux toolchain). Why the mingw ABI is acceptable: the C ABI is plain C with blittable structs, nothing allocated on one side is freed on the other, and no C++ or CRT object crosses it, so the mingw/MSVC differences (C++ mangling and exceptions, `long double`, separate CRT heaps) never reach P/Invoke. ARM64 is plain ARM64, not ARM64EC: Unity's Windows ARM64 Editor and player are native ARM64 processes.
- C runtime: the mingw CRT objects are linked in and the CRT itself is the system UCRT through `api-ms-win-crt-*` API sets (zig's mingw default). Why: UCRT ships with Windows 10+, which Unity 6 requires; no mingw DLL to ship or to collide with another plugin's copy in the Editor; `msvcrt.dll` is legacy. `verify` fails on any import outside the pinned set and checks the PE machine of each DLL.
- `QueryInterruptTime` is imported from `api-ms-win-core-realtime-l1-1-1.dll`, where Windows 10 exports it (mingw's `kernel32` import library lacks it). Kept over `QueryUnbiasedInterruptTime`, which stops during sleep and would break the clock `docs/abi.md` promises.
- mbedTLS threading on Windows is `MBEDTLS_THREADING_ALT` over SRW locks and condition variables, installed by `plat_tls_init()` first in `process_init` (`platform/windows_tls.c`; a no-op in `posix.c`, other platforms keep `MBEDTLS_THREADING_PTHREAD`). Why: mbedTLS 4.1 offers only pthread or ALT, and its `mbedtls_threading_set_alt` must run before any mbedTLS call, `psa_crypto_init` inside `curl_global_init` included; winpthreads (zig carries its source) would be another emulation layer over the same primitives `platform/windows.c` already uses. `mbedtls_threading_free_alt` is never called: SRW locks own no resources, so nothing leaks when the DLL or the process goes away. The glue is a separate file because `ugo-smoke.exe` links it without the rest of the shim.
- `native/deps/threading_alt.h` declares pointer-sized stand-ins, checked against `SRWLOCK`/`CONDITION_VARIABLE` with `_Static_assert`: mbedTLS includes it from every unit that sees `mbedtls/threading.h`, curl's included, and `windows.h` there would spread its macros.
- **No AES/PMULL instructions on ARM64:** `MBEDTLS_AESCE_C` is off for `_WIN32` + aarch64, so AES and GCM's GHASH run in mbedTLS's portable C. Why: mbedTLS detects the Armv8 crypto extensions at runtime only on Linux and assumes them elsewhere (`MBEDTLS_AESCE_HAS_SUPPORT()` is 1 in `aesce.h`), while Microsoft's ARM64 ABI makes them optional (`PF_ARM_V8_CRYPTO_INSTRUCTIONS_AVAILABLE`): the DLL held 64 such instructions and would fault on a CPU without them. A Windows check inside mbedTLS's AESCE code would be a patch to a pinned dependency. Cost: software AES and GHASH, several times slower per byte than the instructions (not measured; bulk TLS throughput only, handshakes are dominated by public-key work), and 2560 bytes of DLL. `verify windows-arm64` disassembles the DLL and fails on `aese`, `aesd`, `aesmc`, `aesimc`, `pmull`, `pmull2`. Linux and Android arm64 keep AESCE behind mbedTLS's `getauxval` check; Apple arm64 always has the extensions.
- Importers: x64 for the Editor (Windows, x86_64) and Standalone Win64; ARM64 for the Editor (Windows, ARM64) and Standalone Win64 ARM64. No PDB: zig can emit one with `-g`, not wired (debt.md *Windows symbols*).
- **Runtime check without Windows:** Wine 10.0 from Debian trixie in a container, one runner per architecture, built by bootstrap from `WINE_BASE_IMAGE` (`linux/amd64`) and `WINE_ARM64_BASE_IMAGE` (`linux/arm64`, native on an arm64 Mac; the arm64 manifest of the same trixie index) plus the sha256-locked Debian packages in `tests/wine/packages.lock` and `packages-arm64.lock`, one shared `tests/wine/Dockerfile`. Why trixie: bookworm's Wine 8.0 aborts on `QueryInterruptTime` (unimplemented); sid has 10.0 as well. Why built, not a public Wine image: Debian-signed packages pinned by hash only, nothing from a third-party publisher in a repo meant to go public. The x64 image is about 2 GB: Debian's `libwine` depends on multimedia libraries even without recommends. Nothing is installed on the Mac (Homebrew's Wine casks are disabled). Debian's arm64 `ntdll.so` carries the BTI property while its hand-written syscall dispatchers have no landing pad, so on a CPU with BTI (Apple M4) every syscall from PE code raises `SIGILL` and `wineboot` spins forever; the Dockerfile clears that one bit, and fails the build if the note is not found.
- `verify windows-x64` and `verify windows-arm64` run the Linux smoke unchanged as `ugo-smoke.exe` plus `ugo-dll-probe.exe`, which loads the shipped DLL by path and makes requests only through its exports (`docs/testing.md` *Tooling*). The native unit tests are not ported: they are POSIX code (pthreads, `unistd.h`, `fcntl`), and the bench binds the Mac's 127.0.0.1 with certificates for loopback names only, which a container cannot reach; Wine is a load-and-smoke check, not a second test platform.

## Size and performance against UnityWebRequest (2026-11-06)

- **Size budget:** `libugo` ≤ 1.25 MiB (`LIBUGO_MAX_BYTES` in `scripts/versions.env`) per ABI, checked by `./scripts/verify`. Raise it only with a reason in this file. APK deltas are compared over an empty player: Unity strips `libunity.so` per used module on Android, so UnityWebRequest is not free.
- **Pass criteria of the benchmark** (manual, numbers in README *Benchmarks*): no worse than UnityWebRequest on CPU and throughput, fewer managed allocations; RSS is reported, not a criterion. 0.2.2 meets it on a Xiaomi 24129PN74G and a Pixel 7a with the mbedTLS configuration above; measured medians are in README *Benchmarks*.
- **No RSS parity:** the contract does not promise resident memory no worse than UnityWebRequest. It states what holds: resident memory grows with the number of open connections, and `MaxConnections` is the caller's bound. Why: the first UgoHTTP client grows RSS by about 1 MiB, mostly the native library's pages loaded once per process (each further client 50–130 KiB), which UnityWebRequest, already resident in the engine, does not show, while after eight parallel 2 MiB downloads and 3 s idle UgoHTTP grows less than UnityWebRequest; which side retains more depends on how many clients and connections an app holds. Where the memory can be cut is open: debt.md *The first client costs about 1 MiB RSS, mostly library code*.

## No PIPEWAIT (2026-11-04)

- `CURLOPT_PIPEWAIT` stays off: parallel requests started before the first connection to a host has negotiated its protocol each open their own connection (about 93 KiB PSS per extra connection on Pixel 7a); later requests multiplex over HTTP/2.
- Why: in curl 8.23.0 a transfer waiting on PIPEWAIT is not woken when the connection settles on HTTP/1.1 (ALPN h1 or cleartext), so parallel HTTP/1.1 requests serialise behind the first. No local curl patch; `https1_parallel_not_queued` in `native/tests/test_ugo.c` guards it.

## Unity package delivery and releases (2026-11-05)

- Consumers add the package to `Packages/manifest.json` by git URL with `?path=package#vX.Y.Z`; versions are git tags and branches. OpenUPM, when the repo goes public, tracks the same tags.
- `master` holds sources only: `package/` with committed `.meta` files (fixed GUIDs, required because a git-installed package is immutable and Unity ignores assets without metas), native binaries never committed there (`package/Plugins/` ignored).
- The `upm` branch mirrors the repo layout: the package sits in `package/` with every shipped plugin and its import-settings `.meta`; each release is a tag on that branch. Why: one artifact for every consumer, binaries out of `master` history, no Git LFS requirement on consumers; one install path shape for every ref, the same subpath as `master` (owner's call).
- `./scripts/package <dir>` writes that tree: tracked `package/` files and every shipped plugin with its `.meta` from `native/unity/`, refusing a non-empty directory and any missing artifact; the same `out/` gives the same tree (`tree_sha256`).
- Until a CI release job exists, releases are cut locally with `./scripts/release X.Y.Z` after a full green gate on the clean release commit; it assembles `upm` and creates its annotated tag, leaving pushes to the operator. The target is CI building every target, running the gate and committing `upm` the same way.
