# Architecture

How the library is built. Principle: the thinnest layer over libcurl that meets `docs/contract.md`. Why each choice was made: `docs/decisions.md`.

## Layers

```
Unity glue              quit / domain reload → shutdown (only Unity-aware code)
C# API (UgoHttp)        requests, WebSocket, events; no UnityEngine reference
   │  P/Invoke, fixed C ABI (`ugo_*`), no variadics
C shim                  command queue → native thread; event queue → C#
   │  platform/         threads, mutex, monotonic clock, file IO: POSIX, Windows; iOS background task
libcurl 8.23+ (static) + nghttp2 + mbedTLS + zlib
```

No backend interface, no transport abstraction. A future UnityWebRequest fallback (WebGL, unported consoles) is a second implementation of the same public C# types, selected at compile time per platform, not an interface chosen at runtime. It is added when a platform needs it, not before.

## Threading

- One native thread per client owns the `CURLM` and every easy handle; curl handles are never touched from another thread. curl's threaded resolver adds short-lived resolver threads; nothing else does.
- Network IO, TLS and file writes all run on that thread. The caller's threads only enqueue commands and drain events, both O(1) and lock-short. No caller code ever runs on the native thread.
- More throughput than one core gives (e.g. TLS on many parallel downloads) comes from more clients, each with its own thread, never from sharing a `CURLM`. Measure before adding a second client by default.
- **Process-wide init** (once, before the first owner thread starts): `plat_tls_init` (installs mbedTLS threading on Windows, *Build*), `curl_global_init`, then `mbedtls_ssl_list_ciphersuites()` to finish mbedTLS's lazy ciphersuite-list initialization, which otherwise races between two clients' first handshakes (found under TSan). mbedTLS is built with `MBEDTLS_THREADING_C`: pthreads on POSIX, `MBEDTLS_THREADING_ALT` on Windows.
- **Managed drain.** Chosen per client at creation (decisions.md *Public C# API shape*). Background (default): one managed thread per client, started by the first `Send`, `SendAsync` or `OpenWebSocket` (`EnqueueDetached` has nothing to drain), blocks in `ugo_wait_events`, completes awaitables and runs callbacks and event handlers on itself, and exits once shutdown has drained every event. Manual: `TryWaitEvents` on the caller's thread does the same inside the call and returns the events of raw `Submit` operations. Both paths share one per-slot table filled on the drain path (completion copy, callback, awaitable source, cancellation registration, pins). One managed drain at a time per client, from the native wait through the dispatch of its batch; a concurrent second drain returns false during disposal and otherwise throws; a reentrant second drain always throws. Every completed payload of a batch is recorded per slot before any user code runs, so a `Dispose` from inside the batch (callback, handler or continuation) delivers each completion with its real result; it drops undelivered headers and progress events. A callback or continuation is never invoked under the client lock; an exception escaping a callback is rethrown on the thread pool. The drain thread starts with execution-context flow suppressed: callbacks run in its own context, not the first sender's. A `CancellationToken` only calls `ugo_abort`: the operation still completes through its one `completed`, after its borrowed memory is unpinned.
- **No Unity loop.** Transfers progress and complete whether or not anyone drains events. Nothing time-dependent (starting queued transfers, connection reuse, timeouts, WS control frames, closing files) runs on the drain path. The C# core assembly has `noEngineReferences`; its tests run in plain .NET.

### Owner loop

1. Commands (submit, abort, ws_send, ws_close, shutdown) are pushed to the command queue, then `curl_multi_wakeup`. The queue is the only carrier of work; a wakeup only means "look at the queue", wakeups may merge, and a command is published before its wakeup.
2. The owner drains all commands, calls `curl_multi_perform`, reads every `CURLMSG_DONE`, services open WebSockets until `CURLE_AGAIN`, then sleeps in `curl_multi_poll` (open WS sockets in `extra_fds`).
3. A transfer reaches its terminal state in exactly one place, `finish(transfer, class)`, on the owner thread: it copies results and `CURLINFO_*` metrics, removes the easy handle (never from inside a curl callback), closes or deletes the file, then emits `completed`.
4. A fatal `CURLMcode` finishes every outstanding transfer with `Internal`.

### Ids, abort, release

- A transfer id is `(slot, generation)`, never a pointer. Any call with a stale id returns an error code and does nothing.
- Exactly one `completed` per transfer. `abort` only marks the transfer; the owner then finishes it as `Aborted` **if it has not finished yet**. If it already finished, the earlier `completed` stands and `abort` is a no-op. Events already queued for a transfer may still arrive after `abort`.
- After `completed` the transfer's result (memory body, header block, metrics) stays valid until `ugo_release(id)`; release frees the slot and bumps its generation.
- A `detached` transfer emits nothing; `finish` frees its slot directly. `abort` still works on its id until then.

### Events

- Events live in the transfer's slot, not in a shared ring: each slot has fixed places for `headers`, coalesced `progress` and `completed`, each WebSocket a backlog of messages allocated at `ws_open`. A bounded queue of slot indices marks "this slot has undrained events"; a slot is in it at most once, so it holds at most `max_transfers` entries and never overflows. No reservation, no event capacity: `submit` fails only when no slot is free. Per-transfer order is kept by draining a slot's places in order; order across transfers is not defined.
- `headers` is emitted when the header block of the **final** response is complete (after redirects), never on the first body byte (204 and empty bodies have none).
- `progress` coalesces to one pending entry per transfer and is emitted only when a byte count changed. Intermediate progress updates are published at most once every 10 ms per transfer; a count held by that limit is published before `completed`, regardless of the interval, so the last progress carries the final byte counts. curl reports after every read, so an event per report woke the drainer once per network chunk.
- Every event carries a monotonic timestamp taken when the owner thread published it, not when it was drained; a held progress count published at the end carries the completion time.
- `completed` carries the error class, `CURLcode`, HTTP status, version, byte counts, connection reuse and the `CURLINFO_{QUEUE,NAMELOOKUP,CONNECT,APPCONNECT,STARTTRANSFER,TOTAL,REDIRECT}_TIME_T` phases. No separate metrics listener.
- One drainer at a time per client: `ugo_wait_events(buffer, timeout_ms)` (0 = poll; no infinite wait, so a drainer never pins a Unity domain that is unloading); a concurrent second drain fails. Draining from different threads one after another is fine. Wait sleeps on "events present or owner joined" and re-checks after every wake. `ugo_release` acts on a finished slot directly, not through the owner.
- No reverse P/Invoke: no AOT callback, GCHandle or domain-reload hazards.

### Shutdown

Stop accepting commands (a call racing shutdown either lands before it or returns `E_SHUTDOWN` having changed nothing; a blocked `wait_events` keeps waiting) → finish active transfers (`Aborted`) and WebSockets → `curl_multi_cleanup` → join the thread **without a timeout** (no caller code runs on it, so a timeout only turns a bug into a leak). A waiter sleeping through shutdown returns once the join is done, with the remaining events. Shutdown frees nothing: results and the events pointing at them stay readable until `ugo_client_destroy`, which frees everything and is a no-op for a client already destroyed.

### Finish in background (iOS)

`platform/ios.m` holds a `beginBackgroundTask` per flagged transfer; `posix.c` and `windows.c` have no-op versions. The task is begun in `submit` before the client lock is taken (UIKit runs the expiration handler on the main thread, and the handler takes that lock) and stored in the slot. It is ended exactly once: an atomic flag picks whichever of `finish` and the expiration handler comes first, and a handler that runs before `beginBackgroundTask` has returned leaves the end to `submit`. The handler finds its client through the process-wide live-client list (held while it touches the client, so destroy cannot free it underneath), marks the transfer and queues it to the owner, which finishes it as `ABORTED` / `BACKGROUND_EXPIRED` as an abort does; the task is ended before the handler returns.

### Unity glue and Editor

- The glue is a separate tiny assembly: app quit, Editor quit and `AssemblyReloadEvents.beforeAssemblyReload` dispose all clients and close the domain to new clients. In the Editor, `ExitingEditMode` snapshots the core's live clients into a strong set under `DomainSync`; `EnteredEditMode` collects every live client absent from that set under the same lock, then disposes them outside it and drops the set. A null set after domain reload means empty: the old domain's clients were already disposed before unloading. This single sweep runs after the game's `OnDestroy`, so final requests there are accepted before disposal; it never closes the domain. The player quit hook skips the Editor. Nothing references the glue, so it carries `[assembly: AlwaysLinkAssembly]`: without it the IL2CPP linker drops the assembly and the player never installs the quit hook (decisions.md *Glue assembly survives stripping*).
- Edit-time tools use the same API with no pumping. The native library keeps a process-wide list of live clients; the first init in a new domain shuts down any client a previous domain left behind.
- Rebuilding the native plugin needs an Editor restart (a loaded `.bundle`/DLL cannot be replaced), so native work is tested in fresh batchmode processes.

### Tracker

- The Editor window (`package/Editor/UgoHTTP.Editor`, `Window/UgoHTTP/Tracker`) has no registry of live objects: `UgoTracking.Snapshot` walks `UgoClient.Live` under `DomainSync` and, per client not disposed, its slot table under `handle.Sync`. A live row is the client itself or a slot with an id: `Submit`, `Send` or `SendAsync` in flight or with its response not disposed, a WebSocket connecting, open or closed and not disposed, with the messages it holds (last sequence delivered to managed code minus the released one, clamped at zero; written on every delivered message as a plain field store, in players too). A disposed socket that is still aborting is not listed: the library frees its slot itself. Clients collected without `Dispose` vanish with their weak reference.
- `UgoTracking.Enabled` is set only by the editor assembly, at load, so it is always on in the Editor and never in a player; the .NET tests set it themselves. It is checked once per client creation, submit, WebSocket open and client disposal; when on, the slot or client gets a metadata object with the method and URL strings the caller passed, a `Stopwatch` timestamp and, with `StackTraces` (the **Capture Stacks** EditorPrefs toggle), a `StackTrace` with file info. The metadata object also keeps the bytes of the latest progress event, written by the drain, less the `headers` resume offset (progress counts the whole file, `completed` this transfer only); a finished row shows the completed event's byte counts instead. Bytes are HTTP traffic only: a WebSocket gets no progress events and its `completed` byte counts stay 0, since messages go through `curl_ws_recv`/`curl_ws_send` outside curl's transfer counters. Off, no operation metadata or history is allocated, the client-disposal tracker scan is skipped, and release and progress events see a null trace. The tracker type has one static lock object.
- Completed rows: `UgoClient.Release` copies a slot that has metadata into a static ring of 512 rows, under `handle.Sync` then the ring lock (never the reverse), as `Closed`, `Aborted` or `Failed` from its result. `Dispose` copies each slot still held after delivering the leftovers as `Closed with client` (a disposed socket still closing as its result), then the client as `Disposed`, once; the Play Mode exit sweep calls `Reclaim`, which marks both `Reclaimed at Play Mode exit`. `Snapshot` copies the ring before the live walk, so a concurrent release can hide a row for one refresh but never list it twice; it drops ordinary completed rows 10 s after release, while only `Reclaimed at Play Mode exit` counts as leak evidence and stays until evicted; `Closed with client` is neutral and expires after 10 s too. The ring is never allocated in a player. A domain reload clears it with the rest of the statics.
- The window refreshes twice a second while visible and not paused (**Pause**, not serialized; the frozen items keep sorting, grouping, search and copy). Items are kept per `(client, operation id)` across refreshes: a row is formatted when it first appears or its state, result, held count or end changes, so a closed row is formatted once; otherwise only live rows' elapsed text is rewritten, and the IMGUI `TreeView<int>` (with a `MultiColumnHeader`) is rebuilt only when a row appeared, changed or left, or when the table is sorted by elapsed time. Columns have fixed default widths (URL stretches with the window) and a small minimum, not content-sized: any column can be narrowed, overflowing text ends in an ellipsis, and every cell carries its full value as a tooltip. Tree, header, splitter and the grouping toggle are serialized in the window and survive domain reloads; row ids map `(client, operation id)` and keep counting across reloads, so a stale selection never lands on a new object. The id map contains only the current rows; selected logical keys and their ids survive a missing snapshot until the row reappears or the user changes selection. The selected row's stack is formatted once, without `UgoHttp` frames, as `<link=href="…" line="…">` rich text in a selectable label, which the Editor itself opens in the code editor, as the Console does.
- **Group by Host** (on by default): every host gets a parent row holding its rows: host, its live rows plus the host totals, and while collapsed the method and result of its latest request; rows without a URL stay top-level. Rows sort within their group; a group sits where its row nearest the new-rows edge would sort, so a host with fresh activity moves to that edge. Hosts start collapsed; expanded hosts are kept by name in memory, so they survive refreshes and regrouping but not a domain reload. Search lists matching rows flat.
- Host totals: `UgoTracking.Complete` adds every finished operation with a URL host to per-host totals under the ring lock: done (`None` or `HttpStatus`), failed, aborted (an `Aborted` result or none), new connections (`connection_reused` 0 with a nonzero connect time: an approximation, a redirect chain that opened several counts once) and bytes. Detached requests never complete through the tracker and are not counted. Totals live until **Clear Host Totals** or a domain reload; a version counter tells the window they changed. `Snapshot` copies the totals with the completed ring, under the same lock and before the live walk, and a host row shows live rows plus that copy, so a released row is never counted twice. Under **Pause**, **Clear Host Totals** clears the window's copy and keeps the frozen rows. **Keep Finished Hosts** (serialized, off by default) keeps a row for every host in the totals.
- Default order is creation time ascending, then client and operation id: new work appends at the bottom and completion does not move a row. A column sort controls its primary order with the same stable tie-breakers. New rows appear at the bottom for an ascending sort and at the top for a descending one; a view scrolled to that edge stays pinned there (log tail). Otherwise refresh keeps the surviving top row (or a visible selected row) at its previous scroll offset, so insertions or expirations above it do not move the view.
- Copy: the row context menu has **Copy URL**, **Copy Row** (tab-separated cells) and, when a stack was captured, **Copy Stack Trace** (plain text); Cmd/Ctrl+C copies URLs. Each acts on the selection (a selected group means its rows), one line per row.

## ABI

- Fixed C functions, no variadics; opaque client handle; events and parameters are blittable structs (no strings, no `ByValArray`, no object marshalling). Strings and byte views are `{ptr, len}`.
- Their layout is the ABI: the client config carries the ABI version (mismatch fails `create`), and the gate compares `sizeof`/`offsetof` from C with `Marshal.SizeOf`/`OffsetOf` from C#.
- Memory returned by the library is freed only by the library (`ugo_release`); the two sides never free each other's allocations (separate CRTs on Windows).

## Allocations

- Steady state allocates nothing per chunk, per progress update or per event, on either side.
- Native: transfer slots (with their event places) are preallocated; a transfer's buffers are allocated at most once each, except a memory body without `Content-Length` or with a `Content-Encoding` (its `Content-Length` is the wire size, so the first allocation is a hint) and the header block, which grow geometrically (memory body up to `memory_limit`): O(log n) reallocations per transfer, never one per chunk. Body bytes go straight from curl's write callback into the file or the result buffer.
- Managed: events are drained into a reusable array (the caller's in manual mode, the drain thread's own in background); no delegate, closure, `Task` or string per event. `SendAsync` returns a `ValueTask` over a completion source reused per slot, so an operation allocates nothing in the library except a cancellable token's registration. `UgoResponse` is a struct over the slot; the memory body and the header block are `ReadOnlySpan<byte>` over native memory until it is disposed, and header lookup scans the block in place. A caller that needs a `byte[]` makes that one copy itself.
- A content-encoded response costs curl's decoder state once per transfer: a 16 KiB output buffer plus zlib's inflate state and 32 KiB window, freed when the transfer ends; nothing per chunk.
- Every allocation on a hot path needs a reason in review; the benchmark counts managed allocations.

## Bodies

- **Memory:** one native buffer per transfer, capped by the caller's limit; exposed in place until release. The body of a non-2xx response is delivered too (APIs return error JSON).
- **File:** `WRITEFUNCTION` writes the file on the owner thread; close happens in `finish` before `completed`. A non-2xx response leaves no `.part`; its body goes to the memory buffer, capped at `UGO_ERROR_BODY_MAX`.
- **Resume:** the shim's own `Range` header, not `CURLOPT_RESUME_FROM_LARGE` (*Verified upstream facts*). `start` (owner thread) opens the existing file once, `open` without `O_CREAT`/`O_TRUNC` (`CreateFileW` `OPEN_EXISTING`), takes its length as the offset and appends `Range` to the request's header list; the header callback parses `Content-Range` only for such a request and, at the final response, positions or truncates the open file (`plat_file_truncate`) or rejects the response before any body byte is written; the write callback counts the body against the range and the finish checks it is complete, since curl knows only the framing (`Content-Length`, chunked, close, HTTP/2 `END_STREAM`), never the range. Nothing is stored next to the file. `Accept-Encoding: identity` keeps every attempt on the same representation, since ranges count encoded bytes (RFC 9110 §14.1.2) and a decoded file has no offsets in that space.
- **Content coding:** without a caller `Accept-Encoding` the shim sets `CURLOPT_ACCEPT_ENCODING` to `gzip`, so curl sends `Accept-Encoding: gzip` and decodes gzip or deflate before `WRITEFUNCTION`: caps and the file see decoded bytes, while headers, progress and byte counts stay on the wire's encoded bytes. `deflate` is decoded when a server sends it, never advertised (decisions.md *Response compression*). A caller `Accept-Encoding`, or the `identity` one a resumed request carries, leaves the option unset: curl then neither adds the header nor decodes.
- **Upload:** from memory, file (`READFUNCTION`) or `curl_mime`; `SEEKFUNCTION` makes it replayable on redirect. The library reads upload memory until `completed`.
- No pull API for bodies in v1: per-chunk reads across the language boundary cost a transition and allocations per chunk (Cronet). A streaming consumer, if one appears, gets `CURL_WRITEFUNC_PAUSE` and a native ring, not `read()`.
- HTTP redirects are followed inside curl up to the limit, except that a 303 is re-issued by the shim as GET without the body (abi.md *Transfer lifecycle*: `CURLOPT_PREREQFUNCTION` stops curl's next request before it is sent, the handle is re-added with the target curl resolved); WebSocket handshake redirects are the shim's too (abi.md *WebSocket lifecycle*). The library never waits for a caller decision mid-transfer.

## Timeouts and DNS

- `CONNECTTIMEOUT_MS`, `TIMEOUT_MS` (0 = none). Optional per-request `LOW_SPEED_LIMIT`/`LOW_SPEED_TIME` (combined send and receive speed below the threshold for the configured window after connect, classified `Timeout`). This also ends a stalled wait for the first response byte or inactivity during the body; an active upload contributes to the speed.
- `CURLOPT_SERVER_RESPONSE_TIMEOUT` does not apply to HTTP ([docs](https://curl.se/libcurl/c/CURLOPT_SERVER_RESPONSE_TIMEOUT_MS.html)): there is no separate first-byte timer. Deadlines independent of transfer speed are the caller's, built from event timestamps.
- `DNS_CACHE_TIMEOUT` configurable, 0 disables curl's cache (the OS cache stays). Threaded resolver, `NOSIGNAL=1`. Optional `CURLOPT_RESOLVE`.

## WebSocket

- `CURLOPT_CONNECT_ONLY=2`; after the handshake the easy handle stays in the `CURLM` and its socket goes into `curl_multi_poll`'s `extra_fds` (`POLLIN` unless paused or the server closed, `POLLOUT` while a send is blocked). Each loop the owner services every open socket: reads with `curl_ws_recv` until `CURLE_AGAIN`, writes until the send buffer is empty or the socket is full, then checks the open and close deadlines, which also bound the poll timeout. curl stops applying `CURLOPT_TIMEOUT_MS` once a `CONNECT_ONLY` transfer is connected, so the open timeout is the shim's own.
- **Handshake:** the shim sets its own `Sec-WebSocket-Key` (PSA random, the expected Accept is PSA SHA-1 + base64; curl sends a caller-set key as is) and checks the 101 as RFC 6455 §4.1 asks before emitting `headers(101)`, which means open: one matching `Sec-WebSocket-Accept`, `Upgrade`, `Connection`, no `Sec-WebSocket-Extensions`, and a `Sec-WebSocket-Protocol` only if it is one the request offered (curl 8.23 verifies none of them). A non-101 response emits `headers` (status + `Location`) and `completed`; curl fails the refused upgrade before passing the blank line that ends its headers, so the shim emits the collected block in `finish`.
- **Control frames are ours:** `CURLWS_NOAUTOPONG`, PING payload collected in a 125-byte buffer, PONG sent by the owner. curl 8.23's auto-PONG is broken: a lone PING never gets its PONG flushed, and a split PING leaks its prefix to the caller (`lib/ws.c:1560-1568, 1646-1698` at `curl-8_23_0`; the split case is fixed upstream in `148133e0`, the lone case is not). Close: a small state machine answers a server CLOSE and bounds our own close; `abort` drops the socket immediately.
- **Receive:** `curl_ws_recv` writes straight into the backlog, a ring of `max_backlog_bytes` allocated at `ws_open`, at the end of the message being reassembled; a message is always contiguous, and when it reaches the end of the ring it moves once to the start if the released space there holds it (one `memmove` per wrap, never per chunk). Control frames between fragments land in the free space and are copied out to a 125-byte buffer. Text and binary: curl reports the message type on every fragment, the backlog entry keeps it, and only text is UTF-8-validated before `ws_message`. A message stays valid until released. After a protocol error the shim stops calling `curl_ws_recv` and drops `POLLIN` for that socket: only its CLOSE goes out.
- **Slow consumer:** when the backlog limit is reached (messages emitted and not yet released, plus the partial one) the owner stops calling `curl_ws_recv` for that socket, except while closing, when it keeps reading and drops data frames to see the server's CLOSE: TCP back-pressures the server, nothing is lost, nothing grows. Control frames wait too, so a server may time the connection out; that surfaces as a normal close.
- **Send:** `ugo_ws_send` validates text as UTF-8 in place, then copies the message into the socket's send buffer, a ring allocated once at `ws_open` (caller-set size), behind an inline 8-byte header holding the length and the type; FIFO per socket, one frame per message. A message that wraps the ring goes out as one frame in two `curl_ws_send` calls (`CURLWS_OFFSET` with the total length); a partial send resumes from its cursor. PONG and CLOSE frames go only between messages, since curl treats any call during an unfinished frame as more of its payload. A full buffer or a socket that is not open fails the call synchronously. No send-completion event: failures surface in the socket's `completed`.
- No permessage-deflate: curl does not support extensions, and the shim does not add it (decisions.md *Contract scope for a public library*); a caller `Sec-WebSocket-Extensions` header is invalid input.

## TLS and trust

**mbedTLS 4.1 LTS everywhere** (LTS until March 2029, [branches](https://github.com/Mbed-TLS/mbedtls/blob/development/BRANCHES.md); curl's [changelog](https://curl.se/changes.html) lists "mbedtls: add support for 4.0.0"; WSS over 4.1 with curl 8.23 confirmed in *Spike checks*).

- Why: one backend → one behaviour and one test configuration on every platform; smallest of the candidates; plain CMake build; pure C with no OS dependency, so it ports to consoles.
- Protocols: TLS 1.2 with AEAD suites only, and TLS 1.3. AES-GCM uses the one-block cipher layer to call AES directly; the generic cipher layer is disabled (decisions.md *mbedTLS configuration*).
- Trust: Mozilla CA bundle (MPL-2.0; pinned PEM source and redistribution notices in `package/Third Party Notices.md`) compiled in, refreshed from curl's `cacert.pem`; the caller may replace it at runtime. No filesystem access needed. Each client parses its bundle into an `mbedtls_x509_crt`, on the owner thread starting at the first TLS connection, and caches only a successful parse. It hands that chain to every connection from `CURLOPT_SSL_CTX_FUNCTION` (`mbedtls_ssl_conf_ca_chain`); curl gets no `CAINFO_BLOB`, so it neither clones, hashes nor reparses a bundle per connection (*Verified upstream facts*). The chain is owner-thread only and freed in `client_free` after `curl_multi_cleanup`, which closes the last connection pointing at it. Any parse failure frees the partial chain and fails that connection (curl 27 for an explicit allocation error, otherwise curl 58), keeping the PEM for a retry at the next connection: a positive skipped-certificate count can hide a transient allocation failure. A partly parsed bundle is refused whole rather than trusted minus the failures. Cost was 2.0 ms per handshake with the bundle (loopback, macOS arm64), now paid once per client after a successful parse; parsing at the first connection rather than in `ugo_client_create` keeps it off the Unity main thread. The `'\0'` the shim appends to a caller bundle is what makes `mbedtls_x509_crt_parse` read it as PEM.
- Costs accepted: no system trust store (user-installed CAs and corporate MITM proxies are not honoured); revocation only as far as mbedTLS + curl offer; the bundle is only as fresh as the last release.
- Android Network Security Config does not apply to UgoHTTP's native sockets: `cleartextTrafficPermitted=false` (the default for apps targeting API 28+) does not block `http://`, and NSC certificate pinning and user CA settings have no effect.
- Rejected: OpenSSL 3 (several times larger, Perl build); per-platform mix with Schannel/SecTrust (three configurations to test, curl's Apple SecTrust needs an OpenSSL-compatible backend, Android has no native backend for curl).

Peer + hostname verification always on; disabling is a dev-only switch that release builds reject at client creation.

| curl configure | HTTP, HTTPS, WS/WSS, nghttp2, zlib (`CURL_ZLIB`, static `libz.a` built from source), threaded resolver; everything else off, brotli and zstd included. Apple: `HAVE_BUILTIN_AVAILABLE=OFF` to avoid weak imports that require a newer consumer Xcode |

`./scripts/bootstrap` is idempotent and is the only setup step: `brew bundle` (checked-in `Brewfile`: cmake, ninja, zig, uv, …), the pinned NDK revision via `sdkmanager`, `uv sync`, the test container images by digest (the Wine runners are built from `WINE_BASE_IMAGE` plus the sha256-locked Debian packages in `tests/wine/packages.lock` for x64, and from `WINE_ARM64_BASE_IMAGE` plus `tests/wine/packages-arm64.lock` for arm64); then it checks every version against `scripts/versions.env` and fails loudly on a mismatch. Dependency sources (curl, mbedTLS, nghttp2, zlib) are release tarballs pinned by sha256, downloaded once into the immutable content-addressed cache `~/.cache/ugohttp/`. Xcode is checked, not installed (≥ 26.4: older versions break ASan/TSan on macOS 26). On a Windows host (Git Bash) bootstrap first fetches the pinned Python, then extracts uv, cmake, ninja, zig, an HTTP/2-capable curl for the bench and the NDK from sha256-pinned archives (`WINDOWS_HOST_*`) into `~/.cache/ugohttp/tools/<sha256>/`; Docker Desktop and the .NET SDK are system installs, checked against `WINDOWS_HOST_DOCKER_VERSION` and `DOTNET_VERSION`. There zig is passed to CMake as a compiler list (`zig;cc;-target;…`) and archives are made with the NDK's `llvm-ar`, since a shebang wrapper cannot run.

## Portability

Consoles must stay reachable (`docs/contract.md`, *Future platforms*). Rules for native code:

- The shim reaches the OS only through `platform/` (threads, mutex, monotonic clock, file IO, CA source, background-task hold). One implementation for POSIX, one for Windows, and a small iOS file (`platform/ios.m`, see *Finish in background (iOS)*); a console adds its own.
- Only the public libcurl API, no curl internals.
- Static linking only; no `dlopen`, `fork`, signals or environment variables at runtime.
- The C ABI does not expose curl or mbedTLS types, so a console backend may use its SDK's own HTTP/TLS stack behind the same `ugo_*` functions.
- A port maintained outside this repository builds the dependencies from `native/deps` with its own toolchain file. That file may set `UGO_PLATFORM_CONFIG_FILE`, an mbedTLS configuration header that `native/deps/client_config.h` includes last (e.g. a platform's clock and entropy source); it is the only hook, and nothing platform-specific of such a port lives here.

## Verified upstream facts

Checked against curl.se on 2026-11-04.

- **curl ≥ 8.23.0.** CVE-2026-92392 (High): HTTP/2 upload use-after-free on `RST_STREAM`, curl 8.12.0–8.22.0 ([advisory](https://curl.se/docs/CVE-2026-92392.html)).
- **Resume in curl.** `CURLOPT_RESUME_FROM_LARGE` does not fit the contract (`lib/http.c` at `curl-8_23_0`): a `200` to a resumed GET fails with `CURLE_RANGE_ERROR` (2745–2765), a `200` whose length equals the offset is "already downloaded" and its body skipped (2749), any `416` is not a failure and its body ignored (508–510, 3814–3818), and `Content-Range` is compared by its first number only (3404–3408). Hence the shim's own `Range` (*Bodies*).
- **CA blob per connection** (`lib/` at `curl-8_23_0`). Each new connection clones `CAINFO_BLOB` into its config (`url.c` 2408 → `vtls/vtls_config.c` 67, malloc + memcpy of the whole blob), hashes it with SHA-256 into the TLS session cache key (`vtls/vtls_scache.c` 297), and `mbed_load_cacert` parses it into a fresh `mbedtls_x509_crt` (`vtls/mbedtls.c` 497–520), first duplicating a PEM blob whose last byte is not `'\0'`; a partly parsed blob (positive result) is accepted with the failed certificates dropped (530). Matching a request against a pooled connection compares the blobs with `memcmp` (`vtls/vtls_config.c` 159).
- **CA chain from `CURLOPT_SSL_CTX_FUNCTION`** (`lib/` at `curl-8_23_0`, mbedTLS 4.1.1). `mbed_connect_step1` loads curl's own CAs first (`vtls/mbedtls.c` 1049); with no blob, file or path that is an empty `mbedtls_x509_crt` (495), since the build sets `CURL_CA_BUNDLE`/`CURL_CA_PATH` to `none`, so no default is filled in (`vtls/vtls_config.c` 290–302), and no native store is used without Apple SecTrust or `CURL_CA_NATIVE` (286–289). `mbed_configure_ssl` always sets `MBEDTLS_SSL_VERIFY_REQUIRED` with curl's verify callback (875–879), which clears flags only for a disabled `VERIFYPEER`/`VERIFYHOST` (455–460); it sets its chain (982) and the hostname (995), and calls the SSL_CTX callback last (1026–1031), so the callback's `mbedtls_ssl_conf_ca_chain`, which only stores the pointer (mbedTLS `ssl_tls.c` 1679–1684), replaces curl's empty chain. A callback error fails the connect with that code. Without the callback the chain stays empty and verification fails `NOT_TRUSTED`: nothing falls open. The callback runs inside `curl_multi_perform`, on the thread driving the multi. TLS sessions live in the multi's cache (`multi.c` 303, `vtls/vtls_scache.c` 371–374; no share) and the connection pool is the multi's; neither key nor match looks at the callback (`vtls/vtls_scache.c` 285–302, `vtls/vtls_config.c` 145–176), which is safe with one multi and one chain per client. `mbedtls_close` frees curl's own `cacert` and the config, not the borrowed chain (1447–1454); pooled and shutting-down connections are closed in `curl_multi_cleanup` (`multi.c` 3035–3036). `mbedtls_x509_crt_verify` only reads the trusted list (`x509_crt.c` 2484–2600). `mbedtls_x509_crt_parse` returns the number of certificates it skipped when at least one parsed (`x509_crt.c` 1496–1502).
- **Negative DNS cache.** Since 8.16.0 failed resolves are cached for half the DNS TTL (default 60 s); since 8.22.0 only "name does not exist" is cached ([docs](https://curl.se/libcurl/c/CURLOPT_DNS_CACHE_TIMEOUT.html)). A request sent while offline must not keep failing after the network returns; `DNS_CACHE_TIMEOUT=0` removes the question.

## Spike checks

Settled by a runtime probe against curl 8.23.0 (2026-11-04): status and `Location` of a failed handshake are readable; partial frames up to 63-bit lengths are delivered with `offset`/`bytesleft`; `Sec-WebSocket-Accept` is not verified; a server CLOSE gets no automatic reply; auto-PONG is broken (see *WebSocket*).

Settled by a second probe (curl 8.23.0, mbedTLS 4.1.1, macOS arm64, against the fault bench, 2026-11-04):
- WSS over mbedTLS 4.1 handshakes (101) and echoes through `CURLOPT_CONNECT_ONLY=2` in a `CURLM`.
- After the handshake, the socket from `CURLINFO_ACTIVESOCKET` in `curl_multi_poll`'s `extra_fds` wakes the poll on incoming data; an idle poll sleeps its full timeout (the finished handle does not make it spin); an HTTP transfer driven in the same `CURLM` does not consume WebSocket bytes.
- `curl_multi_remove_handle` + `curl_easy_cleanup` of an open WSS returns in under 0.1 ms, also with a stalled HTTP transfer in the same `CURLM`; no leaks (`leaks --atExit`). Abort sends no CLOSE, as designed.

## Deliberately not done

Own HTTP parser, TLS, DNS resolver or WebSocket framing (curl frames; the shim only handles control frames and the handshake check); HTTP/3; RFC cache; automatic retries; callbacks into caller code; global state without an explicit client.
